# **Тестовое задание: мини-AdEx (роутер аукционных запросов)**

## **Контекст**

Мы делаем рекламную биржу (ad exchange). Упрощённо это работает так:

1. От площадки (сайта, приложения) приходит **запрос на аукцион** – «у меня есть рекламное место, покажи мне что-нибудь».  
2. У нас есть список **партнёров-DSP** – рекламных платформ, которые готовы купить это место.  
3. Не каждому DSP имеет смысл слать каждый запрос: у партнёров есть ограничения (гео, тип устройства, минимальная цена, отключён ли партнёр вообще). Отбор партнёров под конкретный запрос называется **претаргетингом**.  
4. Отобранным партнёрам мы отправляем запрос (параллельно) и отдаём ответ площадке.

Нужно написать упрощённую версию такого сервиса.

**Язык:** Go. **Транспорт:** HTTP, только стандартная библиотека (**net/http**). Сторонние роутеры и веб\-фреймворки использовать не нужно.

## **Что нужно сделать**

### **1\. HTTP-эндпоинт POST /auction**

Принимает JSON:

{  
  "request\_id": "3f0a1c9e-2b1d-4a8f-9c11-7e6b2d0a55f1",  
  "country": "RU",  
  "device\_type": "mobile",  
  "bid\_floor": 1.5,  
  "categories": \["news", "sport"\]  
}

| Поле | Тип | Описание |
| :---- | :---- | :---- |
| **request\_id** | string | Идентификатор запроса, обязательное |
| **country** | string | Код страны в ISO 3166-1 alpha-2 (RU, US, DE), обязательное |
| **device\_type** | string | mobile, desktop или tv, обязательное |
| **bid\_floor** | float | Минимальная цена, которую готова принять площадка. Больше или равно нулю |
| **categories** | \[\]string | Категории контента площадки, может быть пустым |

### **2\. Список DSP-партнёров**

Партнёр описывается примерно так:

{  
  "uuid": "123e4567-e89b-12d3-a456-426655440000",  
  "name": "DSP Alpha",  
  "endpoint": "http://localhost:9001/bid",  
  "is\_enabled": true,  
  "countries": \["RU", "KZ"\],  
  "device\_types": \["mobile", "desktop"\],  
  "min\_bid\_floor": 0.5,  
  "blocked\_categories": \["gambling"\]  
}

Где хранить партнёров – **на ваш выбор**: JSON/YAML-файл, захардкоженный слайс в коде, in-memory map, PostgreSQL, SQLite. Мы не оцениваем выбор хранилища, мы оцениваем то, как оно изолировано от остального кода.

Партнёров должно быть минимум 3-4 штуки, с разными настройками, чтобы фильтрация была наглядной.

### **3\. Претаргетинг (ядро задания)**

Из всего списка партнёров нужно отобрать тех, кому запрос подходит. Партнёр проходит, если выполняются **все** условия:

1. **Партнёр включён** – **is\_enabled \== true**.  
2. **Гео** – **country** запроса есть в списке **countries** партнёра. Пустой список означает «работаю со всеми странами».  
3. **Тип устройства** –  **device\_type** запроса есть в **device\_types**. Пустой список – «любое устройство».  
4. **Минимальная цена** – **bid\_floor** запроса не ниже **min\_bid\_floor** партнёра. Партнёру нет смысла отдавать трафик дешевле, чем он готов покупать.  
5. **Заблокированные категории** – ни одна из категорий запроса не входит в **blocked\_categories** партнёра.

### **4\. Отправка запроса партнёрам**

Отобранным партнёрам отправляем HTTP-запрос **параллельно**, с общим таймаутом (например, 200 мс). Партнёр, не уложившийся в таймаут или ответивший ошибкой, просто не учитывается – весь аукцион из\-за одного медленного партнёра падать не должен.

Реальные ответы DSP разбирать **не нужно** – это не суть задания. Достаточно любого из вариантов:

* поднять простейший мок-сервер, отдающий **200** (можно в том же репозитории);  
* захардкодить мок-клиент, возвращающий успех/ошибку;  
* вообще не ходить по сети, а сделать DSP-клиент интерфейсом с фейковой реализацией.

Главное, чтобы был виден **механизм**: параллельность, таймаут, устойчивость к падению отдельного партнёра.

### **5\. Ответ**

**200 OK** и JSON вида:

{  
  "request\_id": "3f0a1c9e-2b1d-4a8f-9c11-7e6b2d0a55f1",  
  "matched\_dsps": \["dsp-alpha", "dsp-gamma"\],  
  "sent": 2,  
  "succeeded": 1,  
  "duration\_ms": 42  
}

Если под запрос не подошёл ни один партнёр – тоже **200**, но с пустым списком и явным указанием, что отправлять было некому. Это нормальная штатная ситуация, а не ошибка.

### **6\. Логирование**

Каждый запрос логируем: **request\_id**, сколько партнёров подошло, сколько отфильтровалось, сколько времени заняло. Полезно (но не обязательно) логировать причину, по которой конкретный партнёр не прошёл — на проде это самое частое, что приходится отлаживать.

## **Требования к коду**

* **Разделение слоёв.** HTTP-хендлер не должен содержать бизнес-логику, а бизнес-логика – знать о **http.Request** и JSON-тегах  
* **Никаких паник и утечек горутин.**  
* **Обработка ошибок.** Ошибку либо обрабатываем, либо осмысленно пробрасываем наверх. 

**\_ \= err** не считается.

* **Unit-тесты обязательны.** В первую очередь на логику претаргетинга – это то место, где они дают максимум пользы.
